## 执行与数据保存策略

- **SQLite＋本地文件、单进程串行 worker**：适配本地单用户和低写入并发；FastAPI lifespan 管理数据库及 worker，测试可注入隔离实例。HTTP 不通过每请求 BackgroundTasks 并发执行长任务，不新增分布式队列；有明确并发需求后再重新设计。
- **持久化状态作为事实来源**：原始输入、当前范围、查询／读取游标与累计用量保存到数据库；worker 不以旧快照覆盖用户停止。事务不跨网络请求。
- **增量迁移与追加式来源**：已知旧 schema 增量迁移，不重建用户数据库；每运行论文快照与文本保留历史，证据保存时核对字符定位。旧记录缺失的初始范围标记未知，不凭当前输入反推。
- **报告状态与能力一致**（旧流水线；agent 工作区见下文）：实现结构化字段、实验条件比较和可解释覆盖规则，不将模型判断当作质量证明。只有满足当前操作性条件并原子保存综合报告才为 `completed`；检索无结果、达到限制、有限或未综合的成果均生成阶段性报告并为 `partial`；只有服务失败且无可读资料时为 `failed`。引用原文匹配不证明语义支持，真实服务与人工科研质量仍独立验收。
- **分析修订与事实复用**（旧流水线）：依据2026-11-03用户要求完整推进后续方案，研究补充保留原Run和预算，新增`analysis_revision`隔离适用范围；来源/字段契约未变时引用已有事实，新增维度重新分析，旧结果不覆盖。
- **保守比较与停止规则**：同作/版本逻辑分组但保留原始记录，疑似标题不自动合并；未知实验条件不默认一致，不自动排名。旧流水线的初始6组论文、每子问题2组、关注字段60%是保存到Run的操作性规则，不能作为质量达标率；agent 不用这些规则自动停止，报告只按论文统计有证据的基础字段数。
- **本地三格式渲染**：同一报告结构生成Markdown、Word/PDF，下载不发送论文或调用模型。使用已验证可在当前Python 3.9环境导入和完成定向导出的python-docx 1.2.0、ReportLab 4.5.1；中文PDF嵌入随项目分发的OFL字体。
- **实际请求边界计量**：失败请求、重试和 PDF 跳转计入调用，请求发出前计数并保存；被停止或超时取消的调用仍计入，token 记为未知。
- **PDF 获取与解析边界**：逐跳验证公网目标并固定连接 IP，保留 TLS 校验；解析子进程在超时／取消时回收，实际页码和缺失状态保留，不伪造 OCR 或全文读取结果。2026-11-06 起允许 fake-ip 代理使用的基准测试保留段：用户网络下 arXiv 解析到 `198.18.0.0/15`，此前全文下载全部被判为 `unsafe_url`。

- **模型JSON外壳归一化**：依据2026-11-03实际错误诊断已确认返回以Markdown代码围栏开头，对完整、独立且标为json或无语言标记的代码块仅去除外壳，再严格校验JSON对象和业务契约。不完整围栏、附带正文、多段代码块或无效JSON不修补、不重试；处理只发生在适配器输出入口，不分散到对话与研究服务。实际报错中的JSON正文是否有效仍需区分，不能将归一化视为供应商协议兼容性证明。

- **引用位置由程序计算**：依据2026-11-03受限诊断中“摘录原文存在但模型给错字符区间”的实际失败类型，模型只提供来源标识和完整摘录，代码计算全局字符位置；未找到或匹配歧义均拒绝，不扩展到未读范围。2026-11-06 起比较时忽略空白、连字符和 Unicode 兼容形式差异（见文末两节）。持久化Evidence和前端区间契约不变，旧证据不重写。

## 本机设置策略

依据：2026-11-03 用户要求的设置界面、对话删除、多模型与弹窗关闭等基础功能。

- **供应商为配置单位、对话选择型号**：依据2026-11-03用户进一步明确要求，将该设置分类命名为“AI服务”。每家供应商保存名称、协议、地址、单份密钥及多个模型；设置内没有供应商／型号的使用控制。保存不自动选择，只有对话输入区按供应商分组选择具体型号，一次使用一个。
- **模型清单获取与配置分开**：用户要求“获取模型”和下拉多选；从供应商的模型列表接口读取，可搜索、分页、手动输入ID。获取与保存均不执行模型生成，不将列表返回视为所选协议能力验证。
- **本机原子保存与迁移**：配置优先于环境变量，服务端文件权限600，密钥不回显。已知旧单模型和多档案结构按协议、地址和凭据相同才合并；保留当前型号和不同凭据，读取不写文件，下一次保存才写新结构。
- **空闲时影响当前连接**：切换模型、编辑／删除当前供应商需等待排队和在途请求结束；其他供应商可编辑。移除当前型号或删除当前供应商会清空选择，不自动选替代型号，不清除历史资料或重置预算。
- **凭据绑定地址**：密钥留空仅保留同一供应商的原值，新供应商不继承凭据；更改地址必须重新输入或清除旧密钥。
- **设置按行为分组**：通用、AI服务、外观、数据管理、研究与用量。界面偏好即时生效、仅当前浏览器保存；不展示模型总开关、统一云端分类、金额预算或自动路由。
- **设置取消统一底栏**：用户要求删除整条底栏及其提示／完成按钮。设置直接关闭，偏好仍即时保存；模型保存与取消放在表单内，操作结果在模型页显示。
- **研究与用量按统计范围呈现**：依据2026-11-03用户要求重做该界面，拆分用量概览与执行上限。概览仅统计当前已加载对话，并允许按历史调研查看各自调用、耗时、轮次、Token 与结束原因；各自使用保存的上限和用量。上限仍只读；未选择对话时默认展示上限。沿用现有轮询更新，不伪造全站／每日统计，不推算缺失Token或费用。
- **会话导出与偏好重置分开**：导出当前已加载会话的 Markdown / JSON，保留实际引用摘录和定位；不是完整资料备份，不导出模型配置、密钥或未发送草稿。恢复默认需确认，只重置界面偏好，对话与模型配置保留。

## 对话管理策略

- **名称与研究问题分离**：会话重命名只改 `title`，不把列表整理变成研究范围变更。
- **可恢复删除**：删除时先停止并取消当前工作，再软删除会话；消息、来源、报告和用量保留，用户可撤销或从回收站恢复。恢复只恢复可见性，不自动重启可能产生费用的请求。
- **独立回收站集中管理**：依据2026-11-03用户要求，回收站改为独立窗口，侧栏继续显示正常历史。搜索、排序、分页与本页多选；批量恢复、确认后彻底删除，以及作用于整个回收站的全部恢复／清空。存储层事务清理仅属于被删会话的数据，保留共用来源；worker标记实际在途会话，结束前不能彻底删除。全量操作不受前端100条历史上限限制，不做自动过期清理。
- **弹窗可退出**：浮层菜单支持点击外部、焦点离开与Esc关闭，研究过程展开区不受影响。设置窗口保存中也可关闭，提交仍继续，结果在对话页反馈；不以禁用关闭键维持异步状态。

## 对话交互策略

- **Codex式对话布局**：依据2026-11-03用户要求重做对话UI并仿照Codex，采用中性黑白灰、紧凑导航、无助手头像的Markdown正文与稳定底部输入区，保留Paper Scout名称和科研功能。后台刷新不插入加载段落，不用无变化的轮询强制滚动；对话模式、停止、引用与用量对应真实已有行为，不添加装饰性的终端、附件上传或权限按钮。
- **Task 复用为会话**：独立保存消息和轮次；旧报告、来源和输入保留，旧任务输入不冒充助手回复。
- **HTTP 排队、发送幂等**：同一 worker 串行处理；请求标识用于发送幂等，不自动重放已发起但中断的模型请求。
- **会话级停止**：停止不依赖工作区已创建，不调用模型；中断该会话所有排队和处理中的消息并取消在途请求。迟到结果不得恢复工作，已发起调用仍计用量。
- **来源与能力披露**：引用核对工作区中已保存的证据，定位存在不等于语义支持；未配置模型时直接提示配置，不用固定模板伪装智能回答。

原“前台对话、后台状态机”“固定动作路由”“安全检查点与暂停所有权”“问答与检索分离”和无模型关键词检索，已由下文“对话 agent”取代。

## 审查修复策略

依据：2026-11-05 用户要求修复项目审查发现的问题。

- **对话按轮限制**：取消会话累计40次调用／900秒的终身额度，改为按轮计算；用量继续累计统计，不做金额限制。长对话不再因累计额度永久不可用。当前每轮上限见下文“对话 agent”。
- **执行上限只读且如实显示**：删除从未生效的可编辑上限与诊断调用设置，设置页显示代码中实际生效的研究与对话上限。
- **暂时性错误有限重试**：模型和 arXiv 的限流、超时、网络错误与 5xx 按有限次数重试，每次尝试计入调用；其他错误不重试（模型拒绝后来也按暂时错误重试，见“模型服务稳定性”）。
- **无结果按阶段性结果处理**（旧流水线）：检索无结果或达到限制时生成阶段性报告并记为 `partial`，缺口写明原因；`failed` 只用于服务失败且没有可读资料。
- **单篇失败隔离**（旧流水线；agent 中单条引文被拒只影响该条）：单篇筛选结果无效、单篇提取格式或证据校验失败只影响该篇；综合失败保留逐篇分析。服务类错误仍终止运行。
- **停止只针对正在进行的工作**：已由“对话 agent”取代，不再有用户暂停的运行。
- **追问来源按论文轮换**：已由“对话 agent”取代，追问时 agent 用工具按需读取原文。

消息、状态、引用与用量的详细契约见 [数据与接口](<03-data-and-api.md>)；交互验收方案见 [开发与评估](<05-development-and-evaluation.md>)。

## 仍需讨论或验证

1. **云端模型服务**：用户自行选择地址与型号。实际供应商对结构化输出等能力的支持及可达性仍需验证；不要在聊天或仓库提供密钥。
2. **隐私及文本发送**：已选择云端模型；具体问题、摘要和全文片段的发送范围，以及供应商的数据处理政策，随实际服务确认。
3. **arXiv 接入**：首期已选 arXiv，但单次网络观察或离线替身不代表持续可达、PDF 下载成功或真实服务验收。当前请求间隔要求至少3秒，接入前核对官方条款；缺失 PDF 链接不拼接，预印本不等于同行评审成果，单一来源不代表整个领域。
4. **全文质量**：文本提取不证明复杂表格或版面解析正确；根据受控样本评估解析质量，再决定是否补充解析器。
5. **评价样本和最低质量阈值**：尚未约定；建立基线并人工核查后制定。流程文档的论文数、轮次和覆盖率是建议，不是科研正确率保证。
6. **真实服务与部署验收**：供应商可选参数兼容性、真实网络链路、依赖安全审计和端到端演示须独立验证；多用户与生产部署不属于当前原型范围。

这些条件不阻止先行开发，但影响真实接入和最终验收。需求或技术选择确认后更新对应设计文档；故障经过与逐次执行结果记录在独立的 `changelog/`，不作为本文件的内容。

## 调研规模、实时进度与提示词（2026-11-06）

依据：用户实际使用时反馈“调研的太少”“长时间不动”，并要求优化系统提示词。规模、补检和进度部分已由下一节“对话 agent”取代；引文定位和提示词集中仍适用。

- **规模**：默认上限调整为 60 次外部调用、1800 秒、4 轮，每条查询取 15 条结果，纳入 15 篇、全文 6 篇；筛选分批进行，不再截断候选。仍是固定上限，不做金额预算。
- **补检优先**：论文或子问题覆盖不足时下一轮补检新论文，不反复精读同几篇。
- **实时进度**：耗时步骤开始前保存 `progress` 事件和当前活动，界面显示当前步骤并本地续算计时；仍为轮询，不引入流式通道。
- **引文定位**：忽略 PDF 排版造成的空白与连字符差异；单字段引用无效只丢弃该字段，不再整篇作废。
- **提示词**：集中到 `backend/app/prompts.py`，给出 arXiv 查询写法（宽进严出、同义词 OR、避免长短语）和逐字摘录规则；硬性约束仍由代码校验。

## 对话 agent（2026-11-06）

依据：用户反馈“我其实想要的更多的是agent式的，而不是工作流式的”，选择“对话和研究合成一个 agent”，并要求注意 agent 的基本能力、协调子 agent，可参考 pi、oh-my-pi。执行规则详见 [对话 agent 与执行规则](<04-agent-workflow.md>)。

- **取代显式状态机**：每个对话由一个 agent 接收全部消息，按对话和工作区决定回答、澄清、检索、精读、写报告或回答追问。删除对话路由、固定阶段流水线和运行级暂停／继续／取消接口。原状态机的优点（阶段可观察、限制可控）由持久化的工作状态、事件和代码执行的上限保留。
- **分工不变**：模型选工具、概括和写作；代码执行工具、计数、上限、引文定位、状态保存和上下文压缩。模型输出不能执行任意代码、命令或 URL。
- **JSON 步骤协议而非原生工具调用**：用户网关目前只验证过 JSON 输出，三种协议的原生工具调用能力未验证。每步一个 `{thought, actions}` 对象，入口 pydantic 校验一次，无效输出连同原因交回模型，连续 3 次无效时进入收尾。网关的 JSON 稳定性仍待真实验证；验证原生工具调用可用后可再评估是否切换。
- **工作区跨轮次**：每个对话一个 `agent=true` 的 Run，保存候选、已读范围、证据、判断和报告；后续轮次不重复下载。
- **执行上限按轮**：每条消息一份额度：30 步、150 次外部调用、1800 秒、10 篇全文、同时 3 个阅读子 agent、每个 8 步。接近上限时提示模型整理；达到上限后再给最多 2 次调用和 150 秒只允许回复，仍失败时由代码按计数生成概况。这些是操作性数值，不是质量保证，也不是金额预算。
- **基本能力**：错误作为工具结果反馈、执行中插话、停止取消在途请求、暂时性错误有限重试、上限与收尾、上下文压缩（保留计划清单）、计划清单、持久化进度、用量统计。
- **阅读子 agent**：`delegate` 把论文交给并行的阅读子 agent，每个只看一篇论文和主 agent 给的要求，看不到对话；共用本轮预算，全部结束后主 agent 才收到汇总，停止时随本轮取消。子 agent 最多 3 个并行，但模型请求同时只发 1 个（见“模型服务稳定性”）。
- **参考 pi／oh-my-pi**：借鉴其插话排队、计划清单、上下文隔离子 agent 和上下文压缩的做法；未引入其代码或依赖。
- **移除无模型模式**：原无模型关键词检索不理解对话，在 agent 下无意义；未配置模型时消息直接失败并提示配置。
- **旧运行**：旧流水线未结束的运行在启动时标为中断并说明原因，不再继续；资料可查看，已纳入论文和已取得原文带入该对话的工作区。旧报告、分析和评估按原结构只读。


## 模型服务稳定性（2026-11-07 至 11-08）

依据：用户实际对话中观察到的网关行为（相关性观察，网关未确认其内部原因或限制）及用户确认的处理方式。

- **内容过滤按暂时错误重试**：同一请求的 `content_filter` 时有时无，拒绝与限流、超时、5xx 一样最多重试 2 次并计入调用。
- **连续无效输出进入收尾**：主 agent 连续 3 次输出不符合格式时进入收尾而不是整轮作废，工作区资料保留。
- **子 agent 失败只影响本篇**：阅读子 agent 的模型调用失败（暂时错误重试后，或其他错误）只结束该篇并把原因交回主 agent；鉴权等全局错误由主 agent 的下一次调用使本轮失败。
- **模型请求整次最长 180 秒**：阅读子 agent 累积多页全文后单次响应实测 26–67 秒，原 60 秒会误判超时；180 秒限制整次请求，而不是 httpx 的分阶段计时。
- **模型请求排队**：网关在 2–3 个请求同时进行时频繁返回 5xx，单个请求正常；用户选择保留 3 个并行子 agent，模型请求同时只发 1 个。代价是精读耗时接近逐篇阅读，一次委派可能用满每轮 1800 秒。
